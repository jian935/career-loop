    中文 vs 英文：同一个引擎，两种真实数据

    career-loop 的词表是中文为主——只用英文数据检验，等于没测 两个数据集都是公开、可自行下载复现

    为什么英文数字更高

    英文公开集只有 5 个大类别，类间边界清晰，判错就直接错； 它的 SALES 一个类就覆盖了中文市场的销售 / BD / 电商运营 / 外贸好几类。

    为什么中文场景本身更难

    中文招聘市场有 300+ 细分行业，同一个岗位天然跨族 （"投资经理"既属证券也属财务），标签本身更模糊； 而且客服 / 助理 / 项目专员这类 JD 描述大半是福利模板，信息量不足。

    分桶 offer 率 分布重叠，没有单调关系

    r ≈ 0 的时候，先看分布 别急着怪引擎

    正反馈组中位分 14 vs 非正反馈组中位分 25——两组分布几乎重叠。 这意味着 r ≈ 0 不是引擎没区分度，而是这批「拿到 offer」和「岗位契合度」本来就不相关。 换更强的打分器也一样。

    r 低有两种成因：① 引擎该给高分的没给（要修引擎）； ② 结果与岗位契合度无关（只能认这个数据）。看分布重叠不重叠才能分清。

    防过拟合：dev / hold-out 拆分

    词表挖掘与标注只看 dev（70%），增益必须在 hold-out 复现才算数。 v0.8.14 中文族识别：dev 77.9→85.9、hold-out 79.2→86.2， hold-out 增益 ≥ dev——过拟合的特征恰好相反。

    防拍脑袋：精确率 ≥60% 闸

    每个候选词先算「族内出现次数 ÷ 全部出现次数」，不到 60% 不收。 v0.8.14 因此拦下 24 个词（「数据分析」只有 14%、「客户服务」13.7%）。 service 52% 的缺口至今没硬凑，就摆在那里。

    防迁就：标注错了改标注

    人工标注集判错了，改标注，不改引擎去迁就（P39 漏 pub_document 就是这么修的）。 被证伪的想法也写在 evidence.md 里（词长加权、咨询/顾问入族），别重走。

    第二意见机制：LLM 族识别后端实测v0.8.17 · 1,838 条真实调用 · 同数据集同标签

    1.5 节确认词表补不动最弱两族，转而把语义模型作为第二意见——不换数据集、不换标签、不换输入字段，岗位名绝不喂给模型（标签来自岗位名，喂了就是泄露）：

    模式any-in / top-1做法
    规则基线86.0% / 56.6%纯词表（平均输出 4.88 个族）
    LLM 单独86.5% / 73.5%不是替代品：漏「咨询/实施/售前」（consulting 28%）
    规则空判才问87.0% / 57.6%省调用，增益有限
    blend（默认）93.4% / 73.5%LLM 首选优先 + 规则补充：service 52%→78%

    两个引擎的盲区几乎不重叠（规则漏短 JD / 同义表达，LLM 漏咨询实施售前），所以并集有效。主链路不接 LLM——校准 r 必须离线可复现；未配 Key 或调用失败自动回退规则并标注。 LLM 数字跨运行 ±0.1pt（temperature 0.2），缓存保证单次运行可复现。完整证据链：docs/evidence.md 1.6 节。

    v0.8.21 起，这个网页自己也能用模型判族——在终端跑 career-loop llm-proxy， 把打印出来的地址与 Token 填进「中文抽取实验室」里的「接入 LLM 族识别」面板即可。 Key 始终留在你自己的机器上，网页只跟 127.0.0.1 说话（绕开 CORS，也不用把 Key 贴进网页）。 网页与 CLI 用的是同一份封闭集提示词（由 sync_web_vocab.py 自动生成， scripts/cross_engine_llm_check.py 逐字校验），所以两边判的族是同一件事。

    试过但没做到的：service / project_mgmt 为什么补不动v0.8.16 · 四条路都有数据

    1. 单词补词：去重 + 排除矛盾记录后，service 的真 miss 仅 8 条，唯一过闸候选「组长」上下文是招聘晋升话术（人工过目否决）；project_mgmt 候选为 0。
    2. 短语级模式：「售后服务」精确率 43.8% 不过闸；模拟加入后族识别增益为 0——any-in 判定下，补词的增益上限 = 能救回的 miss 数，先量上限省掉后续全部弯路。
    3. 语境约束版（v0.8.13 机制反向用）：「回访 + 客服语境」55.6% 最高，仍不过 60% 闸；没有为好看把闸降到 40%。
    4. 人工过目 21 条 miss：约 13 条是标题-正文矛盾（标题写「客服」正文是销售/工程/招聘话术），真缺口 8 条的文本里没有任何合格词。

    数据集两个质量问题也单列透明：标题-正文矛盾 80 条（占 miss 31.1%）、 重复抓取 383 条（20.8%，去重口径 84.6%，`cn_eval_family.py` 现在会打印这两个备注）。 补不动就不补——再进一步需要语义模型，不是更多关键词。完整证据链：docs/evidence.md 1.5 节。

    失效区间同样公开：作者私有投递 r = −0.059（early 口径，关键词饱和）、终局 r = 0.03（分布重叠）、 hr 词表精确率 5%、service 族 52%——全部写进 docs/evidence.md，没有藏。 一条命令跑完全部：python scripts/audit.py && python scripts/coverage.py && python scripts/real_eval_family.py && python scripts/cn_eval_family.py && python scripts/eval_real_jd.py && python scripts/cross_engine_check.py （评测数据集需先执行 scripts/fetch_real_eval_data.py / scripts/fetch_cn_eval_data.py 下载，均不入库）
